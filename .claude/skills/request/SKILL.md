# request: 要望の入口とモード選択

要望の本文(引数または会話)を受けて、次の順に進める。

## 1. モードを決める
| モード | 使う場面 | 流れ |
|---|---|---|
| 要件定義モード | 実装まで見据える、または要望が曖昧・大きい | requirements → feasibility(SR-ID ごと) → implement → verify |
| クイック可否モード | 「ざっくり実現できるかだけ知りたい」 | feasibility(簡易回答)のみ |

- 依頼文に「要件定義から」「要件から」とあれば要件定義モード。「可否だけ」「できるかだけ」「ざっくり」とあればクイック可否モード。
- 指定が無い、両方書いてある、読み取れない場合は、**推測せず1問だけ**聞く。質問文の例: 「要件定義から進めますか(実装まで見据える場合)、それとも実現可否だけ簡易に答えますか?」 回答が来るまで他のファイルを作らない。

## 2. 記録する
- フォルダ: `requests/YYYY-MM-DD-件名/`(日付は今日、件名は要望を表す短い語。日本語可・空白なし・30文字以内を目安)。`output/` 側のフォルダ名もこれと同じにする。
- `request.md` に次を書く: 依頼原文、モード(要件定義/クイック可否)、依頼日。

## 3. 次へ渡す
- 要件定義モード → `requirements` スキルを使う。
- クイック可否モード → `feasibility` スキルを簡易形式で使う。

## クイック可否のあと実装に進みたいと言われたら
クイック可否の結果だけでは実装に進まない。`request.md` のモードを「要件定義(クイック可否から切替)」に更新し、`requirements` スキルを使う。その際、直前の `answer.md` の根拠と影響範囲を要件の前提として引き継ぐ。
