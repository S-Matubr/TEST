# Aras Innovator 社内カスタマイズ 仕様把握・実現可否回答・実装プロジェクト 設計書

作成日: 2026-10-23 / 対象: 社内システム「HND-マルQ Step3」(Aras Innovator R30 ベース)

## 1. 目的と成功基準

### 目的
Aras Innovator をカスタマイズした社内システム(マルQ)について、次の3点を行える Claude Code 上の作業プロジェクトを作る。

1. 仕様を正確に把握できる状態にする。
2. 「こういう機能が欲しい」という要望に対し、実現可否と根拠を答える。
3. 実現可能なものは、Innovator へインポートできる形のパッケージ差分として実装する。

### 確定した前提
- 成果物は**パッケージ差分**(AML / Method / 画面コード)。Innovator 実環境への反映は人が行う(API 経由の自動反映はしない)。
- プロジェクトの形態は **Claude Code 上で使う作業プロジェクト**(独立アプリは作らない)。
- 構成案は **B**(整理した仕様ナレッジ + スキル)。AML 解析スクリプトは今回は作らず、必要になった時点で追加を検討する。
- Aras Innovator のバージョンは **R30**。
- 公式技術書類は、手元の PDF 等を優先し、無い内容は Web の公式サイトで補う。
- 利用者は本システムの開発・保守担当で、要望は日本語の文章で渡される(これは仮定)。
- 要望の扱いには **2つのモード**(要件定義モード / クイック可否モード)があり、依頼時に選べる(3章)。

### 成功基準
- 要望に対し、根拠ファイルと影響範囲を示した実現可否の回答が得られる。
- 実装した差分が、構文・参照・`imports.mf` の整合まで検証され、検証できなかった項目は「未検証」と明記される。
- 後から仕様書を追加でき、既存の原典と矛盾した場合に記録が残る。

```

├─ docs/superpowers/specs/ この設計書
├─ source/                原典(読み取り専用・正)
│   ├─ package/           HND-マルQ Step3パッケージ
│   └─ codetree/          HND-マルQ Step3コードツリー
├─ knowledge/             整理済み仕様ナレッジ
│   ├─ INDEX.md           全体索引(ItemType・Method・画面・LC・WF の一覧と所在)
│   ├─ glossary.md        業務用語と Innovator 用語の対応表(要件定義で使う)
│   ├─ itemtypes/ methods/ lifecycles/ workflows/ screens/ common/
│   └─ open-questions.md  「推測」記述・食い違いの確認状況
├─ docs-official/         Aras R30 公式資料
│   ├─ R30/               手元 PDF とそのテキスト化
│   └─ web-refs.md        Web で参照したページ(URL・取得日)
├─ requests/              要望ごとの回答・実装記録
├─ output/                生成したパッケージ差分
└─ .claude/skills/        requirements / feasibility / implement / verify
                          (+ 要望の入口となる request スキル。モード選択を担う)
```

### 情報の優先順位(矛盾したときの正)
1. `source/`(原典の AML・コード)
2. `docs-official/`(手元の公式資料、R30)
3. Web 上の公式サイト(R30 のページと確認できたものだけ)
4. `knowledge/`(原典から導いた二次情報。根拠ファイルへのリンクを必ず持つ)

### 運用ルール
- 既存の `機能設計書.md` は `knowledge/` へ分割して取り込む。
- `source/` は編集しない。変更は必ず `output/` に差分として出す。
- 現在ルートにある原典フォルダ・PDF・設計書は、実装フェーズで `source/` 等へ移す(移動手順は実装計画で定める)。

### 仕様書の追加
- 後から `knowledge/` に新しい仕様書(Word・PDF・Markdown・Excel 等)を追加できる。追加したものは `knowledge/INDEX.md` に登録する。
- 追加した各文書の冒頭に、出典(作成者・日付・対象バージョン)と信頼度を書く。
- 既存の原典と食い違った場合は原典を正とし、食い違いを `open-questions.md` に記録する。

## 3. スキル(`.claude/skills/`)

### 3.0 request(要望の入口とモード選択)
要望を受けたとき最初に動くスキル。次の2モードのどちらで進めるかを決める。

| モード | 使う場面 | 流れ |
|---|---|---|
| **要件定義モード** | 実装まで見据える、または要望が曖昧・大きい | requirements → feasibility(要件 ID ごと) → implement → verify |
| **クイック可否モード** | 「ざっくり実現できるかだけ知りたい」 | feasibility(要望原文に対して簡易回答)のみ |

- **指示のしかた**: 依頼文に「要件定義から」「可否だけ」のように書くか、`/request` 起動時の引数で指定する。指定が無ければ、最初に1問だけ聞いて選んでもらう。
- クイック可否モードで「可能」と出たあと実装に進みたい場合は、**要件定義モードへ切り替える**。その際、requirements は feasibility の結果を踏まえて作る。クイックの結果だけで実装には進まない。
- どちらのモードでも、根拠の明示と「推測」の明記は同じ基準で行う。違いは要件を整理するか否かと、回答の詳しさだけである。

### 3.1 requirements(業務要件・システム要件の定義)
要件定義モードで使う。`requests/YYYY-MM-DD-件名/requirements.md` を出す。

1. 要望の原文を `request.md` に受ける。
2. **業務要件**を整理する(ID は `BR-001` 形式)。背景と課題、目的と期待効果、対象業務と利用者(役割)、現行業務フロー(As-Is)、あるべき姿(To-Be)、業務ルール、対象外。現行フローは `knowledge/` から引き、現行仕様に基づいて書く。
3. **システム要件**に落とす(ID は `SR-001` 形式)。機能要件(画面・操作・処理・承認フロー・通知)、データ要件(ItemType・プロパティ・関係)、権限要件、画面・帳票要件、移行・既存データへの影響、非機能要件(性能・監査・操作ログ)。各システム要件は、対応する業務要件の ID を持つ(トレーサビリティ表を付ける)。
4. 不明点は依頼者へ1問ずつ質問して埋める。推測で埋めず、未確定は「未確定」と書く。
5. 依頼者の確認を得てから feasibility に渡す。確認前に可否回答・実装へ進まない。
6. 用語は `knowledge/glossary.md` に照らして、業務側の言葉と Innovator 側の言葉を対応付ける。

### 3.2 feasibility(実現可否の回答)
- 要件定義モード: `requirements.md` のシステム要件 ID ごとに判定し、`answer.md` を出す。
- クイック可否モード: 要望原文に対して、判定・根拠・影響範囲の概要・主なリスクを `answer.md`(簡易形式)に出す。

要件定義モードの `answer.md` は次の項目を必ず埋める(クイックでは判定・根拠・影響範囲の概要・主なリスクのみ)。

- **判定**: 可能 / 条件付きで可能 / 標準機能の範囲外 / 現時点で判断不能。
- **根拠**: 該当する `source/` のファイルと `docs-official/` の該当箇所。示せない点は「推測」と明記する。
- **影響範囲**: ItemType・Method・ライフサイクル・Workflow・画面・権限。
- **実現方法**: 設定だけで足りるか、Method や画面コードの変更が要るか。
- **リスクと未確認事項**: R30 での動作差、既存データへの影響、`open-questions.md` に入る項目。

### 3.3 implement(実装)
要件定義モードで、可否が「可能」「条件付きで可能」の要件のみが対象。依頼者が回答に了解してから着手する。実装・検証の記録は、システム要件 ID に対する充足を示す形で `implementation.md` に書く。

1. `source/` は変更せず、`output/<件名>/` に出す。
2. 既存パッケージ(h4.01〜h4.15)は書き換えず、新規パッケージとして出す。既存定義を変える場合は AML の `action` 属性(`merge` 等)で表す。
3. `imports.mf` も生成する。
4. 既存の ID・命名規則(`h4_` 接頭辞など)・コード規約に合わせる。
5. 変更内容を `requests/` に記録する。

### 3.4 verify(検証)
`output/` に出したものに対して次を確認する。

- XML として整合しているか(構文、必須属性)。
- 参照先(ItemType・Method・ライフサイクル)が実在するか。
- `imports.mf` の順序とパッケージ依存が合っているか。
- 変更が `source/` の既存仕様を壊していないか。

Innovator 上で実際にインポートしないと分からない項目は、通ったことにせず「未検証」と明記する。

## 4. 仕様ナレッジの取り込み

### 4.1 `機能設計書.md` の分割
現状は読取担当ごとの章が混在し、ItemType の定義とそれを触る Method が離れている。次の単位に分割する。

| 置き場所 | 内容 | 元の章 |
|---|---|---|
| `knowledge/itemtypes/<名前>.md` | ItemType ごと(プロパティ、関係、Form、画面定義) | F, G |
| `knowledge/methods/` | Method(`h4_*` 約270件)をカテゴリ別に分けて収録 | B |
| `knowledge/lifecycles/` `workflows/` | ライフサイクルと Workflow Map | E, G |
| `knowledge/screens/` | コードツリーの画面(h4_Tree、各種テーブル等) | 第5章 |
| `knowledge/common/` | 権限、値リスト、メニュー/ボタン、メッセージ | E |

- 各ファイルの先頭に、根拠となる `source/` のパスと、元の `機能設計書.md` の該当行を書く。
- 分割時に内容は要約も改変もせず、そのまま移す。
- 原典との突き合わせは、全件ではなく、実現可否の回答に使った箇所をそのつど原典で確認する。確認できた箇所には確認日を付ける。
- 設計書内の「推測」147件は `open-questions.md` に一覧化し、確認が済んだら確定へ更新する。

### 4.2 公式書類(R30)
- **手元 PDF**: `docs-official/R30/` に置き、テキスト化して並べる。各文書の冒頭に文書名・版・入手元を書く。
- **Web 補完**: 手元に無い内容は Aras 公式サイトで調べる。R30 のページと確認できたものだけを使い、URL と取得日を `docs-official/web-refs.md` に記録する。R30 と確認できなければ根拠にせず、「版が未確認」と注記する。
- 公式書類の記述と `source/` が食い違った場合は `source/` を正とし、食い違いを `open-questions.md` に記録する。

## 5. CLAUDE.md の必須ルール
1. `source/` は読み取り専用。変更は必ず `output/` に出す。
2. 回答や実装の根拠は、`source/` のファイルパスか `docs-official/` の該当箇所で示す。示せないことは「推測」と書き、断定しない。
3. 実現可否の回答には、影響範囲(ItemType・Method・ライフサイクル・Workflow・画面・権限)を必ず含める(クイック可否モードでは概要で可)。
4. 要望を受けたら、まず要件定義モードかクイック可否モードかを確認する(指示があればそれに従う)。
5. 要件定義モードでは、`requirements.md` を依頼者が確認する前に可否回答や実装へ進まない。クイック可否の結果だけで実装には進まない。
6. 実装は、依頼者が実現可否の回答に了解してから着手する。
7. 検証できなかった項目は「未検証」と明記し、通ったことにしない。
8. 新しい知見や食い違いは `knowledge/` と `open-questions.md` に反映する。

## 6. `output/` と `requests/`

### `output/<YYYY-MM-DD-件名>/`
- `package/`: 変更後の AML・Method・画面コード。インポート可能なフォルダ構成で、`imports.mf` を含む。
- `CHANGES.md`: 変更したファイル、追加・変更・削除の区別、元のファイルとの対応表。
- `import-notes.md`: インポート順、前提パッケージ、手動で必要な作業、ロールバックの考え方。

### `requests/<YYYY-MM-DD-件名>/`
- `request.md`(依頼原文とモードの指定)、`requirements.md`(業務要件・システム要件。要件定義モードのみ)、`answer.md`(実現可否の回答)、`implementation.md`(実装・検証の記録。要件定義モードのみ)。
- 似た要望が来たときは、過去の回答を先に参照する。

## 7. スコープ外(YAGNI)
- AML 解析スクリプト・自動索引生成(必要になった時点で別途検討)。
- Innovator 実環境への API 経由の自動反映。
- 独立した Web/CLI アプリ。
- `機能設計書.md` の全件突き合わせ(使った箇所のみ確認)。

## 8. 未確定・留意事項
- 既存の原典フォルダ・PDF・設計書のルートからの移動は、実装計画で手順を定める。
- 手元の公式 PDF の所在・版は、取り込み時にユーザーへ確認する。
- 実際の Innovator 環境での動作確認は本プロジェクトの範囲外で、人が行う。
